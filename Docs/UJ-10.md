# UJ-10 - Asignación de metadatos a cada problema del concurso

## Descripción

Permite que el **Administrador de Concursos** registre, para cada problema extraído del ZIP, la información necesaria para su publicación dentro del concurso:

* **Título**
* **Inciso** (`A`, `B`, `C`, etc.)
* **Color Globo** 
* **Tiempo límite** en segundos
* **Memoria límite** en MB

Esta funcionalidad forma parte del proceso de creación del concurso y se ejecuta junto con la validación y carga de los problemas y sus casos de prueba.

---

## Endpoint

**POST** `/api/Concursos/crear`

**URL local:**
`http://localhost:5185/api/Concursos/crear`

### Autorización

* Requiere autenticación mediante JWT.
* Solo puede ser ejecutado por usuarios con el rol:

```text
AdministradorConcursos
```

---

## Objetivo funcional

La historia de usuario UJ-10 permite que, al crear un concurso, cada problema quede registrado con sus propiedades principales y quede correctamente asociado a su inciso dentro del concurso.

En otras palabras, el sistema no solo crea el concurso, sino que también guarda la definición formal de cada problema que lo compone. Porque claro, los humanos no podían dejar eso ordenado desde el inicio.

---

## Datos que se registran por problema

Por cada elemento enviado en `listaProblemas`, el sistema almacena:

* `inciso`
* `titulo`
* `tiempo`
* `memoria`
* `estado = Activo`

Estos datos quedan asociados al concurso recién creado.

---

## Validaciones generales del concurso

Antes de registrar la información, el sistema realiza las siguientes validaciones:

### 1. Validación del usuario autenticado

Se verifica que el token contenga el identificador del usuario.

**Si falla:**

```json
{
  "mensaje": "Token inválido"
}
```

---

### 2. Validación de datos del concurso

Se revisan los datos enviados en el formulario general del concurso.

Esto incluye la información necesaria para poder crear correctamente el registro.

**Si falla:**

```json
{
  "mensaje": "Mensaje correspondiente al error encontrado."
}
```

---

### 3. Normalización del código del concurso

El código se limpia con:

* eliminación de espacios al inicio y al final
* conversión a minúsculas

Esto se hace antes de validar duplicados.

---

### 4. Validación de código duplicado

No se permite crear otro concurso activo con el mismo código.

**Si existe duplicado:**

```json
{
  "mensaje": "Ya existe un concurso activo con ese código."
}
```

---

## Validaciones relacionadas con los problemas del concurso

Antes de guardar los problemas, el sistema valida que la estructura del ZIP y los incisos declarados sean correctos.

---

### 5. Coincidencia entre incisos declarados y carpetas del ZIP

Cada problema declarado debe tener una carpeta correspondiente en el ZIP.

Ejemplo esperado:

```text
A/
B/
C/
```

Si faltan carpetas:

```json
{
  "mensaje": "Faltan carpetas en el ZIP para los incisos: A, B"
}
```

---

### 6. Carpeta no declarada en el ZIP

No pueden existir carpetas con incisos que no hayan sido declarados en `listaProblemas`.

Ejemplo: si solo se declararon `A` y `B`, no se acepta una carpeta `C`.

**Si sobra una carpeta:**

```json
{
  "mensaje": "El ZIP tiene carpetas para incisos no declarados: C"
}
```

---

### 7. Cada inciso debe contener archivos `.in`

Cada carpeta de inciso debe incluir al menos un archivo de entrada.

**Si no tiene archivos `.in`:**

```json
{
  "mensaje": "La carpeta del inciso 'A' no contiene archivos .in"
}
```

---

## Validaciones de los casos de prueba

Estas validaciones aseguran que los archivos de entrada y salida estén correctamente emparejados.

---

### 8. Emparejamiento de archivos `.in` y `.out`

Cada archivo `.in` debe tener su correspondiente `.out`.

**Si falta el `.out`:**

```json
{
  "mensaje": "El archivo 'A/01.in' no tiene su pareja .out correspondiente."
}
```

**Si falta el `.in`:**

```json
{
  "mensaje": "El archivo 'A/01.out' no tiene su pareja .in correspondiente."
}
```

---

### 9. Archivos vacíos

No se aceptan archivos de entrada o salida vacíos.

**Si el `.in` está vacío:**

```json
{
  "mensaje": "El archivo 'A/01.in' está vacío."
}
```

**Si el `.out` está vacío:**

```json
{
  "mensaje": "El archivo 'A/01.out' está vacío."
}
```

---

### 10. Cada inciso debe tener al menos un caso válido

No basta con que exista la carpeta. Debe existir al menos un par válido `.in` / `.out`.

**Si no hay casos válidos:**

```json
{
  "mensaje": "El inciso 'A' no tiene casos de prueba válidos."
}
```

---

## Validaciones de tamaño

El proceso controla el tamaño de los archivos para evitar cargas excesivas.

### 11. Tamaño máximo por archivo

Cada archivo `.in` o `.out` no puede superar el límite permitido por el sistema.

**Si supera el límite:**

```json
{
  "mensaje": "El archivo 'A/01.in' pesa X MB, supera el máximo permitido de Y MB por archivo."
}
```

---

### 12. Tamaño total descomprimido

El contenido total del ZIP no puede superar el límite global de descompresión.

**Si supera el límite:**

```json
{
  "mensaje": "El contenido descomprimido del ZIP supera el máximo permitido de 600 MB."
}
```

---

## Proceso de almacenamiento

Si todas las validaciones son correctas:

1. Se crea el concurso.
2. Se registran los problemas uno por uno.
3. A cada problema se le asignan:

   * título
   * inciso
   * tiempo límite
   * memoria límite
4. Se cargan los casos de prueba asociados.
5. Todo se guarda dentro de una transacción.

Esto garantiza que no queden datos parciales si algo falla a mitad del proceso.

---

## Resultado exitoso

**HTTP 200**

```json
{
  "codigo": "cp2026",
  "mensaje": "Concurso, problemas y casos de prueba creados exitosamente."
}
```

---

## Resultados de error

**HTTP 400**

Puede devolverse cuando:

* el token no es válido
* los datos del concurso son incorrectos
* el código ya existe
* la estructura del ZIP no coincide con los incisos
* faltan carpetas
* sobran carpetas
* faltan archivos `.in` o `.out`
* hay archivos vacíos
* se exceden los límites de tamaño

Ejemplo general:

```json
{
  "mensaje": "Descripción del error."
}
```

---

## Reglas de negocio de la UJ-10

* Solo un usuario con rol `AdministradorConcursos` puede crear el concurso.
* Cada problema debe tener un título, inciso, tiempo y memoria.
* Cada problema debe quedar asociado a su concurso.
* La información debe registrarse de forma consistente.
* Si una validación falla, no se almacena nada.
* El proceso completo debe mantenerse atómico mediante transacción.

---

## Observación

La UJ-10 no describe la carga automática de casos de prueba como objetivo principal.
Eso corresponde a la UJ-09.
La UJ-10 se enfoca en **asignar y registrar los metadatos de cada problema** dentro del concurso.
